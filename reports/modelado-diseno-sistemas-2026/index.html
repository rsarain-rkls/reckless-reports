02 Los 4 Principios Fundamentales
Regla de Oro — No negociable
ALTA COHESIÓN + BAJO ACOPLAMIENTO
Estos dos solos cubren el 80% de las decisiones de diseño. Todo lo demás (GRASP, GoF, SOLID) es consecuencia de esta regla.
Principio 1
Abstracción
¿Qué muestro y qué oculto?
Mostrar solo lo esencial, ocultar el resto. La clase MedioPago expone cobrar(monto) pero no expone si por dentro habla con Visa, Mastercard o Mercado Pago. Es la base de la encapsulación y las interfaces.
interface MedioPago: cobrar(monto: Money): Comprobante class PagoEfectivo implements MedioPago class PagoTarjeta implements MedioPago class PagoQR implements MedioPago
Principio 2
Modularidad
¿Cómo divido el sistema en partes manejables?
Dividir en módulos (clases, paquetes, capas) que se diseñan por separado. Cada uno cumple una responsabilidad bien definida. Demasiada modularidad → fragmentación. Poca → God Classes.
ventas/ ← lógica de la venta inventario/ ← stock y reposición pagos/ ← integraciones infra/ ← BD, mensajería
Principio 3 — Métrica
Cohesión
¿Qué tan relacionadas están las responsabilidades dentro de un módulo?
Alta cohesión (✓ deseable): el módulo hace UNA cosa, bien. Ej: CalculadoraImpuestos.

Baja cohesión (✗ evitar): el módulo mezcla áreas no relacionadas. Si el nombre necesita "And" → baja cohesión.
Test rápido: ¿el nombre de la clase necesita "And"? → Baja cohesión seguro.
Principio 4 — Métrica
Acoplamiento
¿Qué tan dependientes son los módulos entre sí?
Bajo acoplamiento (✓ deseable): los módulos se comunican por interfaces claras y estables.

Alto acoplamiento (✗ evitar): un cambio en uno obliga a cambiar al otro. Efecto dominó.
Tipos (menor → mayor): datos < estructura < control < común < contenido.
Larman
Responsabilidades: Doing vs Knowing
Diseñar es asignar responsabilidades a clases. Una responsabilidad es aquello que un objeto sabe hacer o sabe contestar — no es un método, es una abstracción de mayor nivel.
DOING — Hacer
Acciones que realiza el objeto: crear otro objeto, calcular algo, coordinar, delegar.

Ej: Venta.calcularTotal() · Cajero.procesarItem()
KNOWING — Conocer
Información que mantiene: atributos privados, datos derivados, datos sobre objetos relacionados.

Ej: Cliente.dni · Venta.fecha · Producto.stock
03 Patrones GRASP — 9 Patrones de Asignación de Responsabilidades
Larman
General Responsibility Assignment Software Patterns
No son patrones de código (no se "copia y pega"): son principios de razonamiento. Sirven para decidir dónde poner cada método/responsabilidad, antes del código.
"GRASP responde dónde poner la responsabilidad. GoF da la receta probada para implementarla."
5 BÁSICOS — Cubren el 80% de decisiones
GRASP 1
Experto (Information Expert)
¿Quién tiene la información para hacerlo?
Asignale la responsabilidad a la clase que tiene la información necesaria para cumplirla. Evita pedir datos a otro objeto para decidir afuera (rompe encapsulación).
ChangoMás: Venta.calcularTotal() — Venta conoce sus ítems → es la experta.
GRASP 2
Creador (Creator)
¿Quién debe instanciar este objeto?
B debería crear A si B: contiene a A, agrega a A, registra a A, usa intensivamente a A, o tiene los datos para inicializarla.
ChangoMás: Venta crea Item (composición). GestorVenta crea Venta.
GRASP 3
Bajo Acoplamiento
¿Cómo minimizo dependencias entre clases?
Asigná responsabilidades de modo que minimices el acoplamiento. Delegar a interfaces en vez de clases concretas. Síntoma de falla: cambiar una clase obliga a tocar varias.
ChangoMás: GestorVenta usa Notificador (interfaz), no SMTP directamente.
GRASP 4
Alta Cohesión
¿Cómo mantengo a cada clase enfocada?
Asigná responsabilidades de modo que cada clase tenga responsabilidades estrechamente relacionadas. Síntoma de falla: nombre genérico (Manager, Helper, Utils) o nombre con "And".
ChangoMás: split de GestorCaja god-class en GestorVenta, Notificador, ServicioFiscal.
GRASP 5
Controlador
¿Quién recibe los eventos del sistema?
Asigná la responsabilidad de manejar un evento del sistema a una clase que represente el sistema completo (fachada) o un UC específico. Separa la UI del dominio.

2 variantes: Controlador de fachada (1 por sistema) · Controlador de UC (1 por caso de uso) ← más usado en sistemas medianos/grandes.

Anti-pattern: Bloated Controller — el controlador que concentra toda la lógica (≈ God Class disfrazada).
ChangoMás: GestorVenta.escanear(codigo) — la UI del cajero no sabe nada de Producto, Stock ni Comprobante.
4 AVANZADOS — Refinamientos de los básicos
GRASP 6
Polimorfismo
¿Cómo manejo variantes de comportamiento?
Cuando un comportamiento varía según el tipo, asignalo a una jerarquía de clases usando una operación polimórfica. Elimina los if/switch por tipo (anti-pattern: Type Check). Extensible sin romper el código existente (Open/Closed).
ChangoMás: MedioPago.cobrar() — agregar PagoCripto = solo una clase nueva.
GRASP 7
Fabricación Pura (Pure Fabrication)
¿Y si no hay clase de dominio que sirva?
Cuando ningún concepto del dominio sirve como casa natural de una responsabilidad (o ponerla rompería su cohesión), inventá una clase nueva que no represente un concepto del dominio.
ChangoMás: RepositorioVenta — Venta no debería saber de JDBC ni SQL. Se crea una clase técnica.
GRASP 8
Indirección
¿Cómo evito el acoplamiento directo?
Para evitar el acoplamiento directo entre dos clases, ponelas a comunicar a través de un objeto intermediario. Permite cambiar el lado A sin afectar al B.
ChangoMás: ServicioFiscal intermedia entre Venta y AFIP. Si AFIP cambia protocolo, solo toca ServicioFiscal.
GRASP 9
Law of Demeter
"No hables con extraños" — ¿Con quién puedo hablar?
Un método solo puede invocar métodos de: this, sus atributos directos, sus parámetros, objetos que crea internamente. Evita los "trenes de getters" (a.getB().getC().getD()).
MAL: venta.getCliente().getDireccion().getCalle()
BIEN: venta.obtenerCalleEntrega() (delegación interna).

04 Patrones GoF — Gang of Four (23 patrones)
Gamma, Helm, Johnson, Vlissides — 1994
GRASP es el razonamiento. GoF es la receta probada para problemas comunes.
GoF NO es una biblioteca para copiar y pegar. No se "tienen que usar todos". El mejor patrón es el que el junior del equipo entiende en 2 minutos.
"Meté un patrón cuando aparece la segunda variante, no la primera." — Regla de oro anti-patternitis
Creacionales (5)
Cómo se crean los objetos

Singleton · Factory Method · Abstract Factory · Builder · Prototype

Cómo se componen las clases

Comportamiento (11)

Los 7 Principales — En Detalle
Creacional
1 · Singleton
Intención: Garantizar que una clase tenga UNA sola instancia y proveer un punto de acceso global. Cuándo: configuración global, pool de conexiones, caché compartida. Trampa: hace el código difícil de testear (estado global). Se abusa para "compartir cosas" → termina siendo un God Object.
class ConfiguracionPOS: _instancia = None @staticmethod def get(): if ConfiguracionPOS._instancia is None: ConfiguracionPOS._instancia = ConfiguracionPOS() return ConfiguracionPOS._instancia
Creacional
2 · Factory Method
Intención: Definir una interfaz para crear un objeto, pero dejar que las subclases decidan qué clase concreta instanciar. Cuándo: la decisión de qué tipo crear depende de un parámetro. Conexión GRASP: Pure Fabrication + Polimorfismo + Bajo Acoplamiento.
class MedioPagoFactory: @staticmethod def crear(tipo: str) -> MedioPago: if tipo == "EFECTIVO": return PagoEfectivo() if tipo == "TARJETA": return PagoTarjeta(...) if tipo == "QR": return PagoQR(...) raise TipoDePagoDesconocido(tipo)
Estructural
3 · Adapter
Intención: Convertir la interfaz de una clase en otra que el cliente espera. Permite que clases incompatibles colaboren. Cuándo: librería externa con API que no encaja, sistema legacy que convive con el nuevo. Trampa: no usar Adapter para parchear una mala interfaz propia — si es tuya, corregila.
ChangoMás: ImpresoraLegacyAdapter envuelve LegacyTicketPrinter y expone la interfaz limpia Impresora.imprimir(ticket). GestorVenta no sabe que hay una legacy.
Estructural
4 · Decorator
Intención: Agregar responsabilidades a un objeto dinámicamente, sin alterar su clase original. Alternativa a la herencia múltiple para combinar comportamientos opcionales. Cuándo: querés combinar features sin explotar en N subclases.
interface Cobrable: precio(): Money class Item implements Cobrable: ... class DescuentoTarjeta implements Cobrable: base: Cobrable; porcentaje: int precio(): return base.precio() * (1 - porcentaje/100) # Apilable: DescuentoTarjeta(Promocion2x1(item))
Comportamiento
5 · Strategy
Intención: Definir una familia de algoritmos, encapsular cada uno, y hacerlos intercambiables. Cuándo: tenés varias formas de hacer lo mismo y la elección depende del contexto. Elimina los if/switch enormes por tipo. Conexión GRASP: Polimorfismo elevado a patrón concreto.
interface CalculadoraIVA: calcular(precio: Money): Money class IVA21 implements CalculadoraIVA # general class IVA105 implements CalculadoraIVA # carne, pan, frutas class IVAExento implements CalculadoraIVA # libros, leche
Comportamiento
6 · Observer
Intención: Definir dependencia 1-a-N entre objetos: cuando uno cambia de estado, todos sus dependientes son notificados. Cuándo: varios objetos reaccionan al mismo evento sin que el publicador sepa quiénes son. Trampa: si los observadores tardan, bloquean al publicador → async.
class Venta: observadores: List[ObservadorVenta] def cerrar(self): self.estado = "CERRADA" for obs in self.observadores: obs.alCerrar(self) class EmisorComprobante implements ObservadorVenta class ActualizadorStock implements ObservadorVenta class RegistroFidelizacion implements ObservadorVenta
Comportamiento
7 · State
Intención: Permitir que un objeto cambie su comportamiento cuando cambia su estado interno. Cuándo: entidad con ciclo de vida bien definido (los estados del análisis). Elimina el if/switch por self.estado en cada método. Conexión directa: el Diagrama de Estados de B1 se traduce directamente a State pattern.
ChangoMás: Venta → estados Abierta → Cerrada → Facturada → Cancelada. En cada estado las operaciones permitidas cambian. State encapsula cada estado en su propia clase.
Los 16 Restantes — Mini-fichas de Referencia
CAbstract Factory
Crear familias de objetos relacionados sin especificar clases concretas. Ej: SetDispositivosCajaTradicional vs SetDispositivosAutoservicio.
Trampa: sobrediseño cuando hay solo una familia real.
CBuilder
Construir objetos complejos paso a paso separando construcción y representación. Ej: ComprobanteFiscalBuilder.
Trampa: para objetos simples de 2-3 campos, sobra completamente.
CPrototype
Crear nuevos objetos clonando un prototipo existente. Ej: clonar plantilla de promoción y ajustar % por sucursal.
Trampa: clonado superficial vs profundo — bug clásico con referencias compartidas.
EBridge
Desacoplar abstracción de implementación para que evolucionen independiente. Ej: MedioPago (abstracción) × PasarelaTarjeta (implementación).
Trampa: sobreingeniería si hay solo una implementación.
EComposite
Tratar objetos individuales y compuestos uniformemente. Ej: Item y Combo ambos implementan Vendible.calcularPrecio().
Trampa: cuando la jerarquía real no es uniforme, se fuerza un diseño raro.
EFacade
Proveer interfaz simple a un subsistema complejo. Ej: FacadeAFIP esconde 12 webservices detrás de emitir(venta).
Trampa: Facade gigante que termina siendo un God Object.
EFlyweight
Compartir objetos comunes para ahorrar memoria. Ej: datos compartidos de 80k productos cacheados una sola vez.
Trampa: premature optimization si la memoria no es un problema real.
EProxy
Sustituto que controla el acceso a otro objeto (lazy load, cache, auth, logging). Ej: ProxyStockRemoto cachea y sirve último valor si el central está caído.
Trampa: Proxy que termina haciendo más que controlar (= sin cohesión).
BChain of Responsibility
Pasar una request por cadena de handlers hasta que uno la atienda. Ej: ValidadorStock → ValidadorPromo → ValidadorPago → ValidadorFiscal.
Trampa: cadenas largas y opacas donde nadie sabe qué orden importa.
BCommand
Encapsular una operación como objeto (parámetros, undo, queue, logging). Ej: EscanearProductoCommand que se puede deshacer.
Trampa: sumar Command para operaciones triviales que no necesitan undo ni queue.
BIterator
Recorrer una colección sin exponer su estructura interna. Ej: Venta.iterator() sin exponer si por dentro es lista, set o tree.
Trampa: en lenguajes con for-each nativo, implementarlo a mano es ruido.
BMediator
Centralizar comunicación entre varios objetos para reducir acoplamiento N-a-N. Ej: MediadorCaja coordina pantalla, display, cajón, impresora.
Trampa: Mediator que se vuelve un God Object con toda la lógica.
BMemento
Capturar el estado interno de un objeto para restaurarlo después (undo). Ej: SnapshotVenta para deshacer hasta 5 pasos.
Trampa: snapshot pesado de objetos grandes = memoria explota.
BTemplate Method
Definir el esqueleto de un algoritmo en la clase base, dejando que subclases completen los pasos. Ej: ProcesoCierreVentaBase.ejecutar() define el flujo.
Trampa: herencia rígida — muchas veces Strategy es más flexible.

Definir nuevas operaciones sobre jerarquía de objetos sin modificar las clases. Doble despacho. Ver Sección 05 ↓

Definir una gramática y un intérprete para un mini-lenguaje. Cada regla gramatical = una clase. Ver Sección 05 ↓
05 Deep Dive — Visitor + Interpreter EXAMEN JUEVES
Por qué estos dos van juntos
Interpreter construye el árbol de objetos (la estructura). Visitor recorre ese árbol y le aplica operaciones sin tocar las clases del árbol. Son complementarios: Interpreter crea la gramática, Visitor opera sobre ella.
GoF #22 · Comportamiento
Visitor — Double Dispatch
Definición canónica

"Represent an operation to be performed on the elements of an object structure. Visitor lets you define a new operation without changing the classes of the elements on which it operates." — GoF 1994

Idea central

Visitor separa un algoritmo de la estructura de objetos sobre la que opera. Cada elemento expone accept(visitor), que le devuelve el control al visitor mediante doble despacho (double dispatch): el tipo real del nodo Y del visitor deciden qué método corre en tiempo de ejecución.

Diagrama de clases canónico
<<interface>> <<interface>> ReglaExpresion ReglaVisitor +accept(v): T <=========> +visitAnd(r): T /\ +visitMontoMayorQue(r): T ____|____ /\ | | | ________|________ Monto Tiene And | | | Mayor Categ Evaluar Explicar Auditoria Que Visitor Visitor Visitor Doble despacho: el tipo real del nodo Y del visitor deciden qué método corre.
Código ejemplo — Caso motor de descuentos
interface ReglaVisitor[T]: visitMontoMayorQue(r): T visitTieneCategoria(r): T visitAnd(r): T interface ReglaExpresion: accept(v: ReglaVisitor): T class And implements ReglaExpresion: izq: ReglaExpresion; der: ReglaExpresion def accept(self, v): return v.visitAnd(self) # delega al visitor → double dispatch class EvaluarVisitor implements ReglaVisitor: def visitMontoMayorQue(self, r): return self.carrito.total > r.monto def visitAnd(self, r): return r.izq.accept(self) and r.der.accept(self) # La MISMA regla, tres operaciones, CERO cambios en MontoMayorQue / And: regla.accept(EvaluarVisitor(carrito)) # true/false regla.accept(ExplicarVisitor()) # texto legible regla.accept(AuditoriaVisitor(ventaId)) # JSON para logs
Cuándo SÍ usar Visitor
Jerarquía estable Operaciones nuevas frecuentes Separar responsabilidades Recorridos compartidos
Los tipos de nodo cambian poco, pero se necesitan operaciones nuevas seguido (evaluar, explicar, auditar, exportar, migrar). Las clases de dominio quedan libres de lógica de presentación, logging o serialización.
Cuándo NO usar Visitor
Jerarquía volátil Pocas operaciones (1-2) Testing aislado difícil
Si los tipos de nodo cambian seguido → agregar uno obliga a modificar TODOS los Visitors (rompe Open/Closed al revés). Con 1-2 operaciones estables alcanza un método virtual simple. Cada Visitor concreto conoce todas las clases concretas.
GoF #23 · Comportamiento
Interpreter — Gramática como Objetos
Definición canónica

"Given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language." — GoF 1994

Idea central

Dado un lenguaje (gramática simple), Interpreter representa cada regla gramatical como una clase capaz de interpretarse a sí misma. Una expresión compleja se arma combinando expresiones más chicas (≈ Composite); cada nodo evalúa su propia porción de la sentencia.

Diagrama de clases canónico
<<interface>> ReglaExpresion + interpretar(carrito): bool /\ ____|_________ | | Terminal NoTerminal Expression Expression (Composite) MontoMayorQue And / Or / Not TieneCategoria − izquierda: Regla EsClientePremium − derecha: Regla +interpretar() +interpretar(): combina hijos
Código ejemplo — Reglas de descuento e-commerce
interface ReglaExpresion: interpretar(carrito: Carrito): bool class MontoMayorQue implements ReglaExpresion: # Terminal def __init__(self, monto): self.monto = monto def interpretar(self, carrito): return carrito.total > self.monto class TieneCategoria implements ReglaExpresion: # Terminal def interpretar(self, carrito): return carrito.tieneCategoria(self.cat) class And implements ReglaExpresion: # NoTerminal (combina) def __init__(self, izq, der): self.izq, self.der = izq, der def interpretar(self, carrito): return (self.izq.interpretar(carrito) and self.der.interpretar(carrito)) # "total > 50000 AND categoria = Electronica" regla = And(MontoMayorQue(50000), TieneCategoria("Electronica")) aplica = regla.interpretar(carritoDelCliente) # → True/False
Cuándo SÍ usar Interpreter
Gramática simple Reglas volátiles Piezas reusables
Pocos tipos de terminales y combinadores (AND/OR/NOT). Reglas que cambian más que el código (Marketing configura vía panel). Las mismas terminales se recombinan en muchas reglas distintas.
Cuándo NO usar Interpreter
Gramáticas complejas Vocabulario sin límite Alto volumen
Gramáticas con precedencia, funciones, strings → usar parser real (ANTLR). Cada condición nueva = una clase Terminal nueva. Recorrer árbol por evaluación es más lento que código compilado.
Visitor vs Interpreter — La diferencia clave
Interpreter crea la estructura. Visitor opera sobre ella.
Son patrones complementarios, no competidores. Interpreter te da el árbol de objetos que representa las reglas. Visitor te permite agregar operaciones sobre ese árbol sin tocar sus clases. La jerarquía que Interpreter define es exactamente la que Visitor recorre.

Anti-patterns para no olvidar en el examen
Visitor todopoderoso: un Visitor que accede a detalles internos de cada nodo en vez de operar solo a través de la interfaz pública — rompe encapsulamiento.

God Grammar (Interpreter): el DSL crece hasta ser un lenguaje de programación completo, no documentado y sin tooling — peor que el código que reemplazó.
